## Problem Statement

AI-native startups (post-seed to Series A) are giving production agents write-access to critical systems (databases, CRMs, payment processors, deployment pipelines) faster than their engineering teams can build governance around those agent actions. The canonical failure mode: an LLM-driven agent with production credentials hallucinates and executes a destructive action that is difficult or impossible to reverse.

Founder's origin scar: day-job On-Call Agent for Data Engineering team, with Airflow DAG and production Snowflake write access, hallucinated SQL and DELETED columns and tables from production Snowflake. Recovered, but the pattern persists across Sales/CSM teams at the same company running similar agent tools with no governance layer.

Today, engineering orgs handling this pain build ad-hoc Slack-approval wrappers per-agent-per-tool. These fail to scale across multiple agents, multiple frameworks, and the inevitable distributed-systems edge cases: retries during approval windows, cross-agent coordination on shared entities, exactly-once execution when webhooks drop, state machines for approved-then-failed transitions.

The founder has 104 self-dogfooded governed actions on Statis itself (GitHub merges, deploys, migrations) as proof the pattern holds for at least one workflow domain.

## Status Quo

What AI-native startup CTOs do today when an agent needs production write-access:

1. **YOLO path.** Ship the agent with full creds. Hope it does not hallucinate anything destructive. Works until it doesn't. (Founder's own original path.)
2. **Hand-rolled Slack wrapper.** 30-50 lines of Python wrapping destructive tool calls in `requests.post()` to a Slack webhook with approve/deny buttons, state in Postgres, polling for result. Ships fast. Breaks in weeks 2-8 as retries, cross-agent coordination, state-machine edge cases compound.
3. **Framework-native interrupts.** LangGraph has human-in-the-loop interrupts, Anthropic tool-use has pre-execution hooks, OpenAI function-calling allows inspect-before-execute. These are workflow primitives, not governance records. They do not compose across frameworks. They do not produce an audit trail.
4. **Full homegrown governance platform.** 3-6 engineer-months. Few startups do this before they have to.

## Target User & Narrowest Wedge

**ICP:** AI-native startup CTO or platform/infra engineer, post-seed to Series A, running production agents, either post-incident or incident-nervous. Python-dominant stack (LangGraph, CrewAI, Anthropic/OpenAI agents). NOT Fortune 500. NOT enterprise. NOT "AI teams" generically.

**Narrowest wedge:** A single Python decorator, `@statis.gate`, dropped on any function an agent calls that touches a production system.

**Public API signature (v0.2.0):**

```python
@statis.gate(
    action_name: str,                    # required; semantic identifier for policies
    mode: Literal["sync","async","auto"] = "auto",
    on_error: Literal["fail_closed","fail_open"] = "fail_closed",
    timeout_s: int = 300,                # decorator-wait timeout (sync only)
    idempotency_key: str | Callable | None = None,
    runtime: Literal["crewai","langgraph","temporal","plain"] | None = None,
    entity: Callable[[], dict] | None = None,  # optional state snapshot supplier
)
def your_function(...): ...
```

- `mode="auto"` (default): inspects the decorated function. If it is `async def`, treat as async; else treat as sync. Explicit `mode="sync"` or `mode="async"` overrides.
- Sync call: blocks up to `timeout_s`, raises `ActionPending(action_id, resume_url)` on timeout. Async call: returns a `PendingAction` awaitable that resolves when the human decides.
- `on_error="queue"` (local SQLite durable queue) is deferred to Week 2; day 1 ships `fail_closed` + `fail_open` only.
- Day 1 ships `runtime="plain"` + hash-fallback dedup only. `runtime` auto-probes for CrewAI / LangGraph / Temporal ship in Week 2.

**Behavior:**
- First call in production: function does not execute. Statis returns a signed single-use approval URL (Slack integration is Week 2).
- Dedup via `idempotency_key` (caller-supplied or framework-native when the Week 2 probes land). Hash fallback: `SHA-256` over `(agent_id, action_type, canonical_args_hash)`, where `canonical_args_hash` = `SHA-256` of RFC 8785 JCS bytes. Tenant is injected server-side.
- Human approves via web page. Function unblocks. Receipt written, cryptographically hash-chained, from action one.
- **Trojan-horse policy graduation (retention mechanic):** after the 3rd **identical** approval within a 48-hour window, the approval page surfaces a pre-filled YAML policy derived from the approved action's argument shape, with a message referencing the exact pattern (e.g. *"this is the 4th `apply_discount` you've approved for a customer under $500 this week. Auto-approve these going forward?"*). "Identical" = same `action_type` AND same `canonical_args_hash`. User edits two values, saves, future matches auto-approve. User writes policies without realizing.

## Premises (all 6 locked)

1. **Wedge customer** = AI-native startup CTO or platform engineer, post-seed to Series A, running production agents, post-incident or incident-nervous.
2. **Primary product at launch** = `@statis.gate` Python decorator with `mode="auto"` dispatch (sync + async). Sync default timeout 5 min (decorator-wait); approval URL TTL 30 min (distinct clock, see Technical Details). Idempotency keyed on caller-supplied or framework-native identifiers with JCS canonicalized SHA-256 hash fallback, tenant-scoped.
3. **Activation** = signed single-use URL that is a working approval page, not a configuration page. Slack is Week 2. Web page is Day 1.
4. **Core retention mechanic** = Trojan-horse policy graduation. Auto-generated YAML from approved action's argument shape at peak friction. Trigger: 3rd identical approval (same `action_type` + same `canonical_args_hash`) within 48 hours. Every trigger event (fired / accepted / dismissed / edited-and-accepted) logged for funnel analysis.
5. **Defensibility layers by customer lifecycle stage, with dependency order:**
   - Day-0 differentiator (closes sale): state machine + exactly-once + framework-native identity dedup. Without this, the install doesn't happen.
   - Wedge-retention moat (months 1-12): accumulated policy library, cross-framework. ~40 YAML rules that would take a month to rewrite. Without this, customers churn before month nine.
   - Expansion-enabling moat (month 9+): cryptographic receipt ledger, SOC2-exportable. Without this, customers churn just before expansion revenue materializes. **Receipts MUST be written from action one** even if the ledger tooling ships in Q3. Schema is immutable from day one.
6. **Positioning shifts** from "the trust layer for agent runtimes" to **"one decorator. your agent asks permission before it touches production."** Internal architecture still references three pillars; external marketing does not. Package name `statis-ai` stays (PyPI discoverability; renaming would strand the 0.1.0 release).

## Technical Design Details

**Approval URL Security Model.**
- Token format: HMAC-SHA256 over `{action_id, tenant_id, expires_at, nonce}` keyed on the tenant secret.
- **Two independent clocks:** (1) `timeout_s` on the sync decorator is how long the decorator BLOCKS before raising `ActionPending`; (2) URL TTL (default 30 min, max 24h) is how long the approval link remains clickable. The URL can outlive the sync wait.
- Single-use semantics: server atomically consumes the token on first approve/deny click; subsequent clicks render a "this action has already been decided" page with receipt link.
- Authorization scope: token authorizes decision on the specific `action_id` only. No tenant-wide authority.
- Rotation = revocation. Rotating the tenant secret invalidates all outstanding tokens immediately. There is no key-versioning on tokens; short TTL plus manual "re-approve affected actions" page is the rotation-day workflow.
- Primary production channel: Slack approval buttons (Week 2, bot-signed payload). URL is for first-run activation and no-Slack fallback.

**Decorator Failure Modes.**
- `on_error="fail_closed"` (default): API unreachable → raises `StatisError`, agent code handles. Safe default.
- `on_error="fail_open"`: API unreachable → proceed with action, log warning, write deferred receipt when API returns. Opt-in only; intended for non-destructive read actions.
- `on_error="queue"`: local SQLite durable queue, resume on connectivity. **Deferred to Week 2.**
- Process crash mid-wait: action record remains pending server-side, URL remains valid until TTL. Resume via URL click or via re-running agent with same `idempotency_key`.
- Database (Neon) unreachable: API returns 503, SDK retries exponential backoff (100ms / 500ms / 2000ms, 3 attempts), then raises `StatisError`.
- **Uninstall / rollback.** Set `STATIS_DISABLED=1` in environment: decorator becomes a pass-through (function executes immediately, no API call, no receipt). Pending actions remain queryable via the receipt API. Data retained per tenant config. Allows a CTO to remove Statis without code changes.

**Receipt Hash-Chain (schema immutable from action #1):**
- Per-tenant chain. `receipt_N_hash` = SHA-256 of (`receipt_N-1_hash`, `action_id`, `decision`, `conditions_evaluated`, `execution_result`, `timestamp`, `tenant_id`). `entity_state_snapshot` included when supplied by caller via `entity=` callback, else null.
- Concurrent-write safety: T3 of the worker transaction acquires `pg_advisory_xact_lock(hash(tenant_id))` before computing the next hash. Serializes chain writes within tenant, zero contention across tenants.
- Genesis receipt: hash of tenant_id + tenant_created_at.
- Verification CLI `statis verify --tenant=<id>` ships Q2. Does NOT gate prototype.
- Chain forks disallowed. Receipts append-only. Receipt IDs UUIDv7 (time-ordered).

## Reviewer Concerns

Adversarial review ran 3 iterations (max). Final quality: 7/10. 49 issues surfaced; 35 resolved in-doc; 14 remain, listed below. These are implementation-stage decisions, not design invalidations. Resolution happens during Week 1-2 build.

**Completeness**
- **[C1] Entity callback exception.** If `entity=` callback raises, log warning and proceed with null `entity_state_snapshot`. Don't block the action.
- **[C2] action_id allocation.** Server-generated UUIDv7 returned from `POST /actions`. Document in API spec.
- **[C3] Deny-path contract.** Decorator raises `ActionDenied(action_id, reason)` on human deny.
- **[C4] 0.1.0 → 0.2.0 migration.** Deprecation shim + one-release warning when legacy propose/execute is called from top-level `statis` namespace.

**Consistency**
- **[C5] Duplicate Week 2 bullet.** "queue mode" and `on_error=queue` appear twice in Week 2 ship list. Collapse to one.
- **[C6] Async timeout semantics.** `PendingAction` awaitable's timeout behavior (or lack thereof) needs documentation. Default: no timeout; caller wraps in `asyncio.wait_for` if needed.
- **[C7] Runtime literal narrowing.** Decorator signature lists `"crewai"/"langgraph"/"temporal"` as valid Literals but only `"plain"` works Week 1. Either narrow the Literal to `"plain"` for v0.2.0, or make the others raise `NotImplementedError` with an upgrade prompt.

**Clarity**
- **[C8] Identical-predicate noise handling.** Timestamps, request IDs, session UUIDs in args will make `canonical_args_hash` differ on otherwise-identical actions. Either argument-normalization rules (strip known-noisy fields) or a `graduation_key=lambda args: ...` override on the decorator.
- **[C9] Rotation-day re-approve page.** Referenced in security model but not in Week 1 ship list. Mark as Week 2+ explicitly, or add to ship list.

**Scope**
- **[C10] Priority ordering for 104-actions post.** Assignment says "TODAY non-negotiable"; Distribution Plan buries it in Day 1-2. Surface the "TODAY" priority in Distribution Plan too.
- **[C11] Mintlify docs Week 2 vs Week 3 contradiction.** Constraint says Week 2, Distribution Plan says Week 3. Recommend Week 2 alongside launch.

**Feasibility**
- **[C12] Advisory lock collision.** `pg_advisory_xact_lock(hash(tenant_id))` uses Postgres `hash()` which is int4 and will collide across tenants (~1 in 2^31). Switch to `hashtextextended(tenant_id::text, 0)` (int8) or two-arg form `pg_advisory_xact_lock(classid, objid)`. Low-urgency (collision is rare and serialization is still correct) but name the fix.
- **[C13] Week 1 scope realism.** 40 engineering hours for endpoint + signed URL + decorator + hash-chain + advisory locks + graduation UI + YAML generator + Render deploy + demo shoot is tight for one founder moonlighting. Graduation UI is the most time-elastic. Plan for Week 1.5 possible.
- **[C14] JCS library choice.** RFC 8785 has no stable mainstream Python lib. Options: (a) pin a specific implementation (e.g., `pyjcs` if actively maintained), (b) narrower spec: sorted-keys JSON + UTF-8 canonical form + explicit float handling, (c) vendor ~50 LOC. Decision: defer to implementation sprint.

### Async Python Workaround Section (DX-OV-3)

Required README block + `examples/async_workaround.py`:

```python
# Using @statis.gate inside async code (Week-1 workaround until v0.5.0 native async)
import asyncio
from statis import gate

@gate(action_name="send_email")
def send_email_sync(to, subject, body):
    """Underlying function is sync. Decorator wraps it."""
    smtp_send(to, subject, body)

# In your async handler:
async def my_async_handler(...):
    # asyncio.to_thread runs the sync gate-protected function in a thread pool.
    # The event loop stays free to serve other requests during the approval window.
    result = await asyncio.to_thread(send_email_sync, "alice@x.com", "hi", "test")
    return result
```

Required warnings in the README:
1. Don't call `@statis.gate`-protected sync functions directly from a single-threaded event loop (FastAPI sync route, blocking handler) — the entire app freezes until approval. Use `asyncio.to_thread`.
2. Cancellation: when the event loop cancels the awaiting coroutine, the underlying gate call continues until URL TTL — the receipt will show what happened. Idempotency keys protect against double-execution if the caller retries.
3. Native async (`async def` decorator targets) ships v0.5.0; until then, sync-via-thread is the blessed pattern.

### `STATIS_BASE_URL=mock://` Behavior Contract

- **Default:** auto-approve every action after 100ms simulated approval delay; emit deterministic receipt with `decided_via=mock`, ed25519-signed by a hardcoded test key.
- **Configurable via env:**
  - `STATIS_MOCK_DECISION=approve|deny|escalate` — set the default decision
  - `STATIS_MOCK_DELAY_MS=100` — approval delay (default 100)
  - `STATIS_MOCK_PATTERN_DENY=deny_*` — action names matching glob auto-deny (e.g., for testing)
- **In-memory only** — no persistence. Restarting the script resets state.
- **No auth required** — entire mock skips api_key verification.
- **Receipts are real-shape** — same JSON structure as cloud receipts, so test assertions on receipt fields work identically.

### Telemetry Behavior Contract (DX17)

Default: **opt-in on first `statis init`** with a clear prompt: `"Help improve Statis? Anonymous usage telemetry (TTHW, error counts, no PII). Y/n [Y]:"`. Disable anytime via `STATIS_TELEMETRY=0`. CI environments (`CI=true`) auto-disable. Fields sent: hashed install_id (sha256 of machine_id + project_dir), event_type, action_kind hash (sha256, never raw), error_code (from E001+ table), timestamp. Never sent: api_key, action args, hostnames, env values, source paths.
